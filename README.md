# AI FraudShield

> **Proactive protection before the money is gone.**

AI FraudShield is an intelligent digital-banking security layer designed to proactively protect vulnerable and digitally inexperienced customers from suspicious transactions, scams, social engineering, and fraudulent financial activity.

Instead of simply detecting fraud and notifying the customer after a suspicious payment occurs, FraudShield analyzes transaction behavior in real time and introduces additional verification **before the transaction is completed**.

---

## 🚨 Problem

Digital payment fraud can be particularly challenging for:

- Senior citizens
- First-time digital banking users
- Digitally inexperienced customers

A transaction may be technically valid while still being highly unusual for a particular customer.

For example, a customer normally makes transactions between **₹500 and ₹15,000**, but suddenly initiates:

```text
₹75,000 → New Recipient
```

FraudShield identifies this behavioral deviation and proactively intervenes instead of simply allowing the transaction to proceed.

> **Fraud prevention should happen before the money leaves the account.**

---

## 💡 Solution

AI FraudShield is an adaptive security layer that evaluates transactions against a customer's normal behavioral pattern.

The system follows a progressive verification workflow:

```text
Transaction
     ↓
Behavioral ML Analysis
     ↓
Risk Score
     ↓
Risk Classification
     ↓
 ┌───────────┬────────────┬──────────────┐
 │ Low Risk  │ Medium Risk│  High Risk   │
 └─────┬─────┴──────┬─────┴──────┬───────┘
       ↓             ↓             ↓
     Allow       Warning      Face Verification
                                  ↓
                           20-Second Timeout
                                  ↓
                         AI Voice Verification
                                  ↓
                           User Confirmation
                              ↙       ↘
                            YES        NO
                             ↓          ↓
                           ALLOW      BLOCK
```

The core principle is:

> **Low-risk transactions remain frictionless. High-risk transactions receive additional protection.**

## 🧠 Key Features

### 1. Behavioral Fraud Detection

The ML engine analyzes transaction behavior and identifies unusual patterns.

Potential features include:

- Transaction amount
- Average transaction amount
- Historical transaction range
- Amount deviation
- New recipient indicator
- Transaction frequency
- Transaction timing
- Device familiarity
- Location/access anomaly
- Previous behavioral patterns

---

### 2. Explainable Risk Score

FraudShield does not simply display an unexplained risk percentage.

Instead, it provides understandable reasons for the intervention.

Example:

```text
TRANSACTION FLAGGED

Risk Level: HIGH

Reasons:
✓ Amount significantly exceeds normal range
✓ Recipient is new
✓ Transaction behavior is unusual
✓ Transaction timing is abnormal
```

This helps customers understand why additional verification is being requested.

> Risk values shown in demonstrations are examples unless generated by the trained model.

---

### 3. Adaptive Security

Different levels of risk receive different levels of intervention.

| Risk Level | Action |
|---|---|
| Low | Allow normally |
| Medium | Warning + user confirmation |
| High | Step-up verification |

This avoids adding unnecessary friction to every transaction.

---

### 4. Face Verification

High-risk transactions can trigger additional identity verification.

```text
High-Risk Transaction
        ↓
Face Verification
        ↓
Verified?
   ↙          ↘
 YES           NO
  ↓             ↓
Continue    Voice Verification
```

Face verification is used as an **additional authentication layer**, not as proof that the transaction itself is legitimate.

---

### 5. 20-Second Verification Timeout

When face verification is requested, the customer receives a limited verification window.

```text
20 → 19 → 18 → ... → 3 → 2 → 1 → 0
```

If verification is not completed within 20 seconds, the system escalates to voice verification.

---

### 6. AI Voice Verification

If face verification is not completed, the system can initiate a secure voice confirmation flow through the customer's registered communication channel.

Example:

> **AI:** "A transaction of ₹75,000 to a new recipient was initiated from your account. Did you authorize this transaction?"

Possible responses:

**YES**

→ Transaction proceeds.

**NO**

→ Transaction is blocked or held.

**NO RESPONSE / UNCERTAIN**

→ Transaction is temporarily held for safety.

### Security rule

The voice system should **never request**:

- OTP
- PIN
- CVV
- Password
- Card credentials

The voice interaction is for **transaction authorization confirmation only**.

## 🔐 Security & Privacy

FraudShield follows a security-first design.

### Sensitive Information

The system should avoid collecting unnecessary personal information.

### Voice Verification

The voice agent should only confirm transaction authorization and must never request banking credentials.

### Face Verification

Facial information should be securely handled and used only for the intended authentication process.

### Human-in-the-Loop

The ML model provides a **risk assessment**, not an unquestionable final judgment.

```text
ML Risk Assessment
        +
Verification
        +
User Confirmation
        ↓
Final Decision
```

## 🤖 Machine Learning Model

### Overview

AI FraudShield uses a trained **Random Forest Classifier** to assess the fraud probability of every transaction before it is authorized. The model is trained on a synthetic behavioral dataset and produces a **0–100 risk score** that drives the verification flow.

### Dataset

The model is trained on a **synthetically generated dataset** of 15,000 transactions:

| Class | Count | Percentage |
|-------|-------|------------|
| Legitimate | 13,500 | 90% |
| Fraudulent | 1,500 | 10% |

The dataset is generated with realistic behavioral patterns and intentional noise/overlap so that the model must genuinely learn patterns rather than reproduce deterministic thresholds.

> **Note:** This is a hackathon prototype dataset. It is not derived from real banking transaction data.

### Input Features

The model uses exactly **5 behavioural features**:

| Feature | Description |
|---------|-------------|
| `transaction_amount` | Current transaction amount in INR |
| `user_avg_amount` | User's historical average transaction amount |
| `new_recipient` | 1 = first-time recipient, 0 = known recipient |
| `transaction_frequency` | Number of transactions in the recent time window |
| `transaction_hour` | Hour of the transaction (0–23) |

### Target

| Column | Values |
|--------|--------|
| `fraud_label` | 0 = legitimate, 1 = fraudulent |

`fraud_label` is the **training target only** — it is never used as a prediction input.

### Model Architecture

- **Algorithm:** `RandomForestClassifier` (scikit-learn)
- **Trees:** 100 estimators
- **Class weighting:** Balanced (handles 90/10 imbalance)
- **Train/test split:** 80% / 20%, stratified
- **Random state:** 42 (reproducible)

### Model Performance (on held-out test set)

| Metric | Value |
|--------|-------|
| Accuracy | 99.2% |
| Precision | 97.3% |
| Recall | 94.7% |
| F1 Score | 95.9% |
| ROC-AUC | 99.9% |

### Feature Importances

| Feature | Importance |
|---------|-----------|
| `transaction_amount` | 43.2% |
| `transaction_frequency` | 28.4% |
| `transaction_hour` | 11.4% |
| `new_recipient` | 10.8% |
| `user_avg_amount` | 6.3% |

### Risk Score Mapping

```
fraud_probability × 100 = risk_score (0–100)

0–29   → LOW RISK    (normal transaction flow)
30–59  → MEDIUM RISK (additional confirmation)
60–100 → HIGH RISK   (step-up identity verification)
```

### Backend API

The model is served via a lightweight **FastAPI** server:

```
POST http://127.0.0.1:8000/predict

Request:
{
  "transaction_amount": 75000,
  "user_avg_amount": 4200,
  "new_recipient": 1,
  "transaction_frequency": 8,
  "transaction_hour": 3
}

Response:
{
  "risk_score": 100,
  "risk_level": "HIGH",
  "fraud_probability": 1.0,
  "features": { ... },
  "model_status": "ONLINE"
}
```

### Running the Backend

```bash
# 1. Install dependencies
pip install -r backend/requirements.txt

# 2. Generate synthetic dataset
python backend/generate_dataset.py

# 3. Train the model
python backend/train_model.py

# 4. Start the API server
python -m uvicorn backend.app:app --host 127.0.0.1 --port 8000
```

### Offline Fallback

If the backend is unreachable, the frontend automatically falls back to a **deterministic rule-based scoring engine**. The modal eyebrow clearly shows:

- `ML MODEL` — prediction is from the trained Random Forest
- `OFFLINE MODE` — prediction is from the local fallback
